# 技术选型与开发计划

> 版本：v1.0　|　日期：2026-10-20　|　对应需求：`docs/GestureWebController需求文档.md` v1.3

---

## 一、结论先行

调研了 GitHub / HuggingFace 上全部相关仓库后，得到一个明确判断：

> **不存在"一个仓库拿走就能交差"的完整项目。** 高星的是数据集和 MediaPipe 方案，YOLO 手势仓库普遍是个人作业（零到几十星、无权重、无协议、只有单文件推理脚本）。

因此本项目采用**三层复用**策略，各取所长：

| 层 | 复用什么 | 来源 | 解决的问题 |
| --- | --- | --- | --- |
| 模型层（主干） | HaGRIDv2 官方 YOLO 手势检测权重，34 类开箱可用 | `hukenovs/hagrid` | 免训练直接跑通识别，5/6 手势精确命中 |
| 交互层（参考） | 手势判定、点历史平滑、防抖、Web demo 结构 | `Kazuhito00/hand-gesture-recognition-using-mediapipe` | 手部抖动与误触发处理，业界成熟做法 |
| 框架层 | Ultralytics YOLO 训练/推理/导出 | `ultralytics/ultralytics` | 训练、ONNX 导出、推理 API 统一 |

**自研部分**：Web 全栈（FastAPI 服务 + 前端 SDK + 四表数据库 + AI 问答 + 截屏链路 + 后台管理）。这部分没有任何现成仓库可抄，也正是答辩的技术含量所在。

## 三、6 种手势可行性核对（关键结论）

已下载 `YOLOv10n_gestures.pt`（22.4 MB，HTTP 200 可直连）并用 pickle 解析权重内的 `names` 字段，**实际类别 34 个，与 HaGRIDv2 `constants.py` 完全一致**：

```
grabbing, grip, holy, point, call, three3, timeout, xsign, hand_heart, hand_heart2,
little_finger, middle_finger, take_picture, dislike, fist, four, like, mute, ok, one,
palm, peace, peace_inverted, rock, stop, stop_inverted, three, three2, two_up,
two_up_inverted, three_gun, thumb_index, thumb_index2, no_gesture
```

对照需求文档 3.4 节的 6 种手势：

| 需求手势 | 动作 | HaGRID 类名 | 状态 |
| --- | --- | --- | --- |
| ✌️ V 手势 | 下翻页 | `peace` | ✅ 精确命中 |
| ☝️ 食指上指 | 上翻页 | `point`（备选 `one`） | ✅ 精确命中 |
| 🖐️ 张开手掌 | 截屏 | `palm`（备选 `stop`） | ✅ 精确命中 |
| 👍 点赞 | 确定 | `like` | ✅ 精确命中 |
| 🤞 交叉手指 | 触发图片识别 | `xsign` | ✅ 精确命中 |
| 🤟 爱与和平 | 截屏 + AI 搜索 | **无对应类**，最接近 `rock`（🤘 食指+小指） | ⚠️ 缺口 |

**缺口处理（两选一，建议都做）**：

1. **先跑通（零成本）**：映射到 `rock`，答辩时说明"🤟 与 🤘 在检测层面姿态接近，选用模型已有类别，通过配置映射实现动作"，体现"映射可配置"的设计价值。
2. **后补齐（加分项）**：自采 200~300 张 🤟 样本，与 HaGRID 子集混合，在 ultralytics 上增类微调，产出自己的 `gesture_yolov8n.pt`。同时满足"YOLOv8"表述与"自主训练"加分点。

> **映射与模型的一致性可自检**：`python scripts/check_gesture_map.py` 用标准库直接解析 `.pt` 里的 `names` 字典（无需安装 torch），逐个核对配置里的 `model_class` 是否存在于权重中，缺失时返回非 0。已实测：6/6 命中。

> 权重精度（HaGRID 官方 README 公布）：YOLOv10x 手势检测 89.4，YOLOv10n 88.2。n 版 22MB、CPU 可跑，足够答辩现场。

## 五、分阶段开发计划

> 每天投入 2~3 小时估算，可按答辩日期整体压缩。每个里程碑都以"能演示"为验收标准，不追求全功能并行。

### M0 · 推理服务跑通（约 2 天）

| 任务 | 交付物 | 验收标准 |
| --- | --- | --- |
| 环境与依赖 | `backend/requirements.txt`、`scripts/download_model.py` | 一条命令拉到权重并校验大小 |
| YOLO 推理封装 | `backend/app/services/detector.py` | 输入 numpy 图 → 输出归一化检测结果列表 |
| 抽帧预测接口 | `POST /api/predict`（`backend/app/api/predict.py`） | curl 上传一张图，返回类别 + 置信度 + 框坐标，单帧 < 300ms |
| 模型适配层 | 权重路径、类别映射走配置 | 换权重文件不改代码 |

**风险点**：CPU 推理速度。对策：`imgsz=640`、`half=False`、只保留置信度 > 阈值的框；前端限流 6~8 fps，不必每帧都送。

### M1 · 前端 SDK + 演示主页（约 4 天）

| 任务 | 交付物 | 验收标准 |
| --- | --- | --- |
| 摄像头采集与抽帧 | `sdk/src/capture.js` | `getUserMedia` 正常、关闭后释放资源 |
| 检测结果可视化 | `sdk/src/overlay.js` | Canvas 上画框、类名、置信度 |
| 手势判定与防抖 | `sdk/src/debounce.js` | 连续 3 帧同手势且 ≥0.7 才触发 |
| 动作执行器 | `sdk/src/actions.js` | 滚动 / 截屏 / 模拟点击 三种动作可用 |
| 事件总线 | `sdk/src/index.js` 暴露 `on('gestureTrigger')` | 外部页面可订阅 |
| 演示主页 | `frontend/pages/index.html` | 摄像头 + 控制面板 + 手势列表 + 实时日志 + 长文演示区 |

**阶段成果**：此时已可完整演示"上翻/下翻/截屏/确定"——需求文档 4.1 的核心页面成立。

### M2 · 数据库与账号体系（约 4 天）

| 任务 | 交付物 | 验收标准 |
| --- | --- | --- |
| 四表建表 + ORM | `backend/app/db/`（user / gesture_record / image_record / chat_record，含外键） | 建表脚本可重复执行 |
| 注册登录 | `POST /api/auth/*`，密码 bcrypt 哈希 | 错误密码有明确提示，数据库不存明文 |
| 会话鉴权 | JWT 中间件，区分普通用户/管理员 | 越权访问后台返回 403 |
| 记录上报 | 手势事件异步落库（`gesture_record`） | 演示 10 次手势，库内 10 条记录且带 uid/置信度/时间 |
| 个人中心 | `frontend/pages/profile.html`，三类记录列表 + 删除 | 列表分页、删除即时生效 |

**设计要点**：日志上报必须**异步 + 可关闭**（需求 3.6 的"数据库可插拔"），DB 挂了不能影响手势操控。

> **M2 实际完成情况**：以上全部落地，实测 34 个接口用例通过（`scripts/test_api_m2.py`）。与计划的差异：上报接口用"同步写 + 异常吞掉"而非消息队列——SQLite 单条写入是毫秒级，引入队列会让"10 次手势 10 条记录"的验收变复杂；真正的解耦体现为**失败不影响操控**（ADR-011）。

### M3 · 图像识别三条链路 + AI 问答（约 5 天）

| 任务 | 交付物 | 验收标准 |
| --- | --- | --- |
| 静态图片识别 | `POST /api/image/recognize` | 上传图返回识别文本 + 标签，写入 `image_record` |
| 🤞 手势触发图片识别 | SDK 唤起上传 → 自动提交 → 结果回显 | 全链路 < 3s |
| 🖐️ 截屏 | html2canvas 捕获可视区 | 截图清晰、无跨域缺失 |
| 🤟 截屏 + AI 搜索 | 截图自动上传 → 识别 → 回显预览 + 结果 | 全链路 1~3s，截图存 `data/screenshots/`，记录入库 |
| AI 问答 | `POST /api/chat`，支持流式（SSE） | 首字延迟 < 1.5s，问答对入库 |
| 图文联动 | 识别结果一键填入提问框 | 打通"识别 → 问答"链路 |

**风险点**：截图内容识别质量取决于模型能力，需准备 2~3 个"答辩演示友好"的备选场景（带大字/图表的页面），避免现场翻车。

## 六、接口契约（先定死，前后端并行开发）

```http
POST /api/predict
Content-Type: multipart/form-data
  frame: <jpeg 二进制>        # 前端 drawImage 后 toBlob，质量 0.7
  conf:  0.7                  # 可选，置信度门槛（0~1）；不传则按手势各自的 min_conf
  imgsz: 640                  # 可选，160~1280

200 OK
{
  "ok": true,
  "infer_ms": 52.8,
  "image_size": [426, 256],
  "gestures": [
    { "class": "rock",              // 模型原始类别名
      "id": "love_you",             // 手势语义 id（SDK 事件里返回这个）
      "label": "爱与和平",
      "emoji": "🤟",
      "action": "screenshot_ai_search",
      "action_label": "截屏 + AI 搜索",
      "conf": 0.7976,
      "box": [100.7, 27.5, 126.4, 67.2]   // xyxy，原图像素坐标
    }
  ]
}
```

**辅助接口** `GET /api/health`：返回权重名、是否已加载、类别数、六手势映射、防抖参数，前端可据此判断服务是否就绪（不触发模型加载）。

**错误码**：415 图片类型不支持 / 400 请求体为空或图片无法解析 / 413 超过 4MB / 422 参数越界 / 503 权重缺失 / 500 推理异常。

**M0 实测数据**（Windows / CPU / YOLOv10n / imgsz=640）：单帧 28~58ms，模型首次加载约 3.2s（已做 warmup，且支持 `GWC_PRELOAD=1` 启动即加载）。HaGRID 样例切片 30 张命中 9 张（palm 0.90、stop 0.91、rock 0.80、peace 0.66、one 0.68）；切片分辨率仅 213×128，真实摄像头画面会明显优于该结果。

**真实素材验收**（用户提供的高清手势图）：✌️ `peace 0.83`、🖐️ `palm 0.94`、🤟 `rock 0.51`（→ love_you）。降质测试（`scripts/stress_test.py`，17 种条件）命中 12、**零误判**，最小可用帧宽 360px，模糊与过曝会漏检。

约定：`gestures` 为空数组表示未识别到手势；前端只在 `conf ≥ 阈值` 且连续 3 帧同类时触发动作，**服务端不做防抖**（防抖属于 SDK 职责，保证工具可复用）。同一手势检出多只手时只返回置信度最高的一条。

**阈值语义（ADR-008）**：服务端是两段式——`candidate_conf`（默认 0.3）只决定哪些框进候选，最终是否算数看每个手势自己的门槛：`min_conf`（写在 `gesture_map.json`）优先，否则用 `model.yaml` 的 `conf`（0.7）。因此 🤟 借 `rock` 类、门槛 0.45 也能触发；而未经配置的类不会因为放宽候选下限而混进结果。`conf` 传参优先级最高，仅供调试。

### 6.2 账号与记录接口（M2 已实现并实测）

鉴权统一走 `Authorization: Bearer <token>`，未带 token 的公共接口按游客处理。

```http
POST /api/auth/register   {username, password, nickname?}  → 201 {access_token, token_type, expires_in, user}
POST /api/auth/login      {username, password}             → 200 同上
GET  /api/auth/me                                          → 200 {user}
PATCH /api/auth/me        {nickname?} 或 {old_password, new_password}  → 200 {user}

POST /api/records/gesture {gesture_type, confidence?, action?, source?, infer_ms?}
     → 201 {saved: true, record}          落库成功
     → 200 {saved: false, reason}         数据库不可用 / 记录关闭（不影响操控）
GET    /api/records/gesture?limit&offset   → 200 {total, items[{record_id, gesture_type, gesture_label, action, confidence, infer_ms, source, create_time}]}
GET    /api/records/gesture/stats          → 200 {stats:{total, by_type, daily, avg_confidence}}
DELETE /api/records/gesture/{record_id}    → 200 {deleted}（只能删自己的，管理员不限）
GET    /api/records/image | /api/records/chat   → 200 {items}（M3 起有数据）

GET  /api/admin/overview | /users | /records    → 需管理员，否则 403
GET  /api/system/status                         → 数据库可用性、四表计数、密钥来源、手势清单
```

**约定**
- `gesture_type` 用语义 id（`victory / point_up / open_palm / thumb_up / cross_fingers / love_you`），**不是**模型类别名；中文名与动作由服务端按 `gesture_map.json` 补齐，客户端不必传。
- 未登录也可上报，`uid` 记 null，个人中心因此看不到游客记录（这是刻意的：游客日志只用于演示统计）。
- `source` 只接受 `camera / video / images / unknown`，SDK 遇到自定义帧源会自动报 `unknown`。

**错误码**：401 未登录或 token 失效 / 403 非管理员 / 404 记录不存在或非本人 / 409 账号已注册 / 422 参数校验失败 / 503 数据库不可用（账号类接口）。

## 八、主要风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 🤟 无对应类别 | 6 种手势只演示得出 5 种 | 先映射 `rock` 并说明，M4 微调补齐 |

| 权重过大不便分发 | 换机跑不起来 | 权重不入库，脚本下载 + 校验 sha256 写进 README |
