为什么把手势做成一门「可嵌入」的能力，而不是一个独立 App

嵌入式示例页 · 手势翻页 / 截屏在这篇文章上直接生效

很多手势项目最后都做成了一个孤立的演示页：打开它、比手势、看它动， 然后就没有然后了。真正要落地，手势必须能被塞进别人已经做好的页面里—— 阅读器、文档站、课件、后台系统。

这篇页面的特别之处

你现在看的这篇文章，是一个独立实现的长页。它并不知道"手势"这回事， 唯一的改动是引入了 9 行代码：

引入 SDK → 给它一张 canvas → await start()。 翻页、截屏、点击，全部由 SDK 的默认动作接管。
  • 比 ✌️ 往下翻一屏，比 ☝️ 往上翻一屏 —— 试试现在能不能翻动这篇文章。
  • 比 🖐️ 抓取当前视口，截图会出现在右侧。
  • 比 👍 点击当前焦点元素。
  • 不想动摄像头？点右侧「用示例图」跑一遍，链路一样走得通。

为什么不直接做一个浏览器插件

插件权限大、能作用于任意站点，但安装门槛高、审核周期长，而且拿不到页面的语义结构， 只能靠模拟事件"盲点"。SDK 方案反过来：宿主页面主动接入，能精确控制作用域 （container 指定滚动容器）、能拿到业务事件（gestureweb:action）， 也不需要任何安装。

边界：它只操控当前标签页

这是刻意的取舍。截屏走 html2canvas 重绘 DOM，而不是 getDisplayMedia；后者能截到桌面和别的窗口，需要二次授权， 对"手势操控网页"这个场景来说是过度授权。SDK 的能力边界就是浏览器标签页之内。

识别在服务端做（YOLOv10n + HaGRIDv2 34 类），前端只负责抽帧、叠框、防抖。 这样换模型、调阈值都不用改业务代码，一处升级处处生效。

性能账

抽帧固定 640px、8fps，单帧推理 28~58ms（CPU）；预览 60fps 独立渲染，不与识别抢主线程。 防抖是 3 帧一致 + 800ms 冷却 + 容忍 1 帧丢失，所以抬手、晃动不会连续触发。

这段文字存在的意义

它足够长，能让你验证"翻页真的翻了"。如果它翻不动，那这套方案就没有意义—— 所以这段是用来被翻的，不是用来读的。你可以用 ✌️ 一直翻到底， 看到页面底部的验收提示。

这里是长文填充区：用 ✌️ 连翻几次，应该能看到这一块在你眼前滚过去。

完整接入代码（9 行） 可复制到任何页面 

<!-- 1. 准备一张画布，SDK 会往上面叠预览和框 -->
<canvas id="cam" width="320" height="240"></canvas>

<script type="module">
import { GestureWebController } from './sdk/src/index.js';

const ctrl = new GestureWebController({
  canvas: document.querySelector('#cam'),
  endpoint: 'http://127.0.0.1:8000',
  fps: 8,
});

await ctrl.start();                        // 开摄像头 + 开始识别
window.addEventListener('pagehide', () => ctrl.stop());
</script>

这页为了让你手动点，把 start() 挂在了按钮上；想进页面就自动跑，直接调用即可。 想接管动作？传 actions: { screenshot: () => {...} } 覆盖默认实现； 想监听事件？ctrl.on('gestureTrigger', cb) 或监听 document 上的 gestureweb:action，不必持有 SDK 实例。
