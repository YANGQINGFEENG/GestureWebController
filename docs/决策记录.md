# 决策记录（ADR）

> 记录"为什么这样定"，避免不同 AI / 不同机器上重复讨论已定的方案。
> 新增决策时复制模板追加，编号递增，**已生效的决策不要删除**；要推翻就新增一条并注明 `取代 ADR-xxx`。

**模板**

```
### ADR-00X 标题
- 日期：YYYY-MM-DD
- 状态：已生效 / 已取代（被 ADR-00Y） / 已废弃
- 背景：为什么需要决定
- 决定：最终选了什么
- 理由：为什么不选其他方案
- 影响：后续开发要注意什么
```

### ADR-001 模型主干用 HaGRIDv2 预训练权重，不自研网络
- 日期：2026-10-20
- 状态：已生效
- 背景：需要识别 6 种手势，从零训练成本高，课程周期不允许。
- 决定：使用 `hukenovs/hagrid`（HaGRIDv2）官方 YOLOv10n/x 手势检测权重，34 类开箱可用；推理框架用 Ultralytics。
- 理由：调研了 GitHub / HuggingFace，其他 YOLO 手势仓库最高 46 星且多为个人作业（无权重、无协议）；HaGRIDv2 有 108 万图 + 官方权重 + 明确协议（CC BY-SA 4.0）。实测权重可直接下载（22,442,394 字节），解析出 34 类。
- 影响：README 必须注明来源与协议，衍生权重同样 CC BY-SA 4.0 共享；权重体积大不入库，用脚本下载。

### ADR-002 手势控制走「前端采集 + 后端推理」（方案 A）
- 日期：2026-10-20
- 状态：已生效
- 背景：需求文档给了两个方案，A 为前端传帧后端推理，B 为前端本地 ONNX/WebGPU 推理。
- 决定：走方案 A。
- 理由：后端推理便于答辩展示 Python + 模型调用链路，调试简单；前端本地推理虽省带宽但增加复杂度，作为加分项保留可能性。
- 影响：前端必须做**抽帧限流**（6~8 fps），缩图后上传；服务端必须保证单帧 <300ms。

### ADR-003 防抖放在前端 SDK，服务端保持无状态
- 日期：2026-10-20
- 状态：已生效
- 背景：误触发会毁掉现场演示；但服务端做防抖又会让接口不可复用。
- 决定：连续 3 帧同类且置信度 ≥0.7 才触发，同手势冷却 800ms，全部在 SDK 内完成。
- 理由：SDK 是交付给第三方网页的产物，接网页面自己的交互节奏应由客户端决定；服务端只负责"这一帧有什么手势"。
- 影响：`/api/predict` 保持无状态；参数（frame/confThreshold/cooldownMs）走 `config/gesture_map.json` 的 `debounce` 段。

### ADR-004 手势映射配置化：id 与 model_class 分离
- 日期：2026-10-20
- 状态：已生效
- 背景：换模型后类别名可能变化，若配置直接以类别名为键，换模型要重写整套配置。
- 决定：`config/gesture_map.json` 用数组结构，每条含 `id`（语义标识，SDK 回调返回）与 `model_class`（当前权重类别名）。
- 理由：语义与模型解耦，换权重只改 `model_class` 一行；`scripts/check_gesture_map.py` 可一键校验配置与权重是否对得上。
- 影响：SDK 加载配置时自行建立 `model_class → gesture` 的反向索引；不要在其他地方硬编码类别名。

### ADR-005 🤟 爱与和平暂时映射到 rock(🤘)
- 日期：2026-10-20
- 状态：已生效（待 M4 取代）
- 背景：HaGRIDv2 的 34 个类别里没有 ILY（🤟）这一姿态，最接近的是 `rock`（食指+小指伸出）。
- 决定：先映射 `rock` 保证六种手势都能演示；M4 阶段自采 200~300 张 🤟 样本增类微调，产出 `love_you` 类后把 `model_class` 改过去。
- 理由：零成本先跑通全链路，避免为了一个手势卡住整体进度。
- 影响：答辩时必须主动说明这个映射关系与后续方案（体现"映射可配置"的设计价值，而不是回避）。

### ADR-006 数据库为可插拔日志层
- 日期：2026-10-20
- 状态：已生效
- 背景：需求要求"不启动数据库工具依然可运行"。
- 决定：手势记录异步上报，失败只打日志不阻断；配置项可整体关闭落库。
- 理由：保证演示时"库挂了手势照样能用"，也符合工具化定位。
- 影响：`backend/app/db/` 不得被手势主链路同步依赖。

### ADR-007 SDK 抽帧宽度不低于 640px
- 日期：2026-10-20
- 状态：已生效
- 背景：用同一张 ✌️ 图做 17 种降质测试（`scripts/stress_test.py`），结果：
  - 帧宽 640 / 480 / 360 命中（0.82 / 0.83 / 0.77），**320px 起漏检**
  - JPEG 压缩到 q20 仍命中，**运动模糊（r≥1.5）与过曝 1.6x 会漏检**
  - 暗光 25%、低对比 50%、旋转 15° 均稳定命中，无误判
- 决定：SDK 抽帧按 640px 宽度输出（`imgsz=640` 与模型训练尺度一致），不为了省流量降到 480 以下；前端提示用户避免强逆光。
- 理由：分辨率是本模型最敏感的因素——降到 320px 直接归零，而 640px 单帧仅 40ms 左右，没有省的必要。
- 影响：M1 的 `capture.js` 固定输出 640 宽；`frontend/pages/index.html` 需带"光线不足/逆光"提示；若后续为省带宽要降分辨率，必须先用 `stress_test.py` 复测。

### ADR-008 阈值改为「两段式 + 按手势可调」
- 日期：2026-10-20
- 状态：已生效
- 背景：用户提供真实 🤟 素材图（`data/testshots/user/4937.jpg_wh860.jpg`）实测，模型把它识别为 `rock` **置信度仅 0.51**，而全局阈值 0.7 会直接丢弃——即 ADR-005 的近似映射在代码层面其实"永远触发不了"。同时另一张双手图会产生 `like 0.34` 的误检。
- 决定：
  1. `model.yaml` 拆成两个参数：`candidate_conf: 0.3`（送进 YOLO 的原始检出下限）、`conf: 0.7`（手势默认门槛）；
  2. `gesture_map.json` 的每个手势可写 `min_conf` 覆盖默认门槛，🤟 设 0.45；
  3. 显式传参（`POST /api/predict` 的 `conf`）优先级最高，用于调试。
- 理由：单帧分数低不等于识别错——🤟 这个姿态本来就没有训练类，属于借类使用，它的分数天然比原生类低一档。用"每类自己的门槛"表达这个事实，比全局压低阈值安全：全局降到 0.45 会把 `like 0.34` 之外的更多误检放进来，而按类放宽只会影响那一个手势。
- 实测（改后）：🤟 图默认参数 → `love_you 0.5099` 命中；`conf=0.95` → 空；`conf=0.2` → 能看到 0.34 的 `like` 候选（证明它存在且被正确拦在门外）。
- 存档值：`0.45 / 0.7` 是**暂定值**，需 M1 用真实摄像头画面校准；调参只改配置、不改代码，改完跑 `scripts/predict_image.py` 复测。

### ADR-009 抽帧来源做成可替换接口
- 日期：2026-10-20
- 状态：已生效
- 背景：开发机没有摄像头，若把 `getUserMedia` 写死在采集层，M1 的防抖、画框、动作执行全都无法验证，只能"写完等有了设备再说"。
- 决定：`FrameSource` 统一暴露 `grab() → {blob,width,height}`，实现三种来源：摄像头 / 本地视频 / 图片序列；上层 `GestureWebController` 不感知来源差异。
- 理由：图片序列每张停留 1.5s，正好能稳定攒够 3 帧防抖窗口，是排查"为什么这个手势不触发"最快的办法；也顺带让演示不依赖现场设备。
- 影响：新增功能不得在 `capture.js` 之外出现 `getUserMedia`；图片序列模式只用于开发验证，答辩演示仍以摄像头为准。

### ADR-010 SDK 防抖阈值只是兜底，不得高于后端门槛
- 日期：2026-10-20
- 状态：已生效
- 背景：`gesture_map.json` 的 `debounce.confThreshold` 原为 0.7，与后端旧全局阈值同值。后端改成按手势门槛后，前端若继续用 0.7，会把 🤟（0.51）在后端放行后**再拦一次**——表现就是"后端明明返回了手势，页面毫无反应"。
- 决定：`confThreshold` 下调到 0.35，仅作异常数据的兜底；真正的手势门槛由后端每类 `min_conf` 决定。防抖参数在前端不硬编码，启动时从 `/api/health` 读。
- 理由：验证逻辑只该有一处权威。两处各写一个阈值，改一处忘一处就会产生"静默失效"——这类 bug 在演示现场最难排查。
- 影响：新增 `scripts/test_sdk.mjs` 的回归用例「🤟 的 0.51 必须能触发」；页面显式传 `debounce` 参数时优先于服务端（供调试）。

### ADR-011 数据库用 SQLite + SQLAlchemy，且必须是"可掉落"的一层
- 日期：2026-10-20
- 状态：已生效
- 背景：需求要求四张表、外键关联、CRUD，同时要求"不启动数据库工具依然可运行"。
- 决定：
  - 存储用 SQLite 单文件（`data/app.db`，启用 WAL + `PRAGMA foreign_keys=ON`），ORM 用 SQLAlchemy 2.0；
  - 引擎**懒加载**：`db/session.py` 里首次访问才建引擎，失败只记日志不抛出到启动流程；
  - 所有 SQL 集中在 `db/repository.py`，API 层不写查询；
  - 记录上报接口 `POST /api/records/gesture` 在数据库不可用时返回 **2xx + `saved=false`**，
    而不是 5xx；账号类接口用 `require_db` 明确返回 503。
- 理由：答辩现场最怕的是"数据库出问题导致手势也不能用"。把记录降级成可掉落的附加能力，演示主线不受影响。
- 影响：`backend/app/api/records.py` 不得依赖 `DbSession`（会 500），必须用 `MaybeDb`；新增数据库配置在 `config/app.yaml`，可用 `GWC_DB_ENABLED=0` 整体关闭。

### ADR-012 认证用 bcrypt + JWT，角色只分 user / admin
- 日期：2026-10-20
- 状态：已生效
- 背景：需要注册登录、个人信息编辑、以及一个能看全站数据的管理员。
- 决定：
  - 密码用 bcrypt（cost 12）存哈希，列名沿用需求文档的 `password`，实际内容是 `$2b$...`；
  - 身份用 JWT（HS256，默认 7 天），payload 只放 `sub`（uid）与 `role`，每次请求回查用户表确认账号仍存在；
  - 密钥优先级：`GWC_JWT_SECRET` > `config/app.yaml` > 自动生成写入 `data/.jwt_secret`（已 gitignore）；
  - 角色用字符串 `user` / `admin`，不建角色表——课程项目两种角色足够，多一层表只增加演示成本；
  - 库为空时自动种一个管理员：默认 `admin / admin123456`，可用 `GWC_ADMIN_USER` / `GWC_ADMIN_PASSWORD` 覆盖。
- 理由：bcrypt 自带随机盐，不引入 passlib（它对 bcrypt 5.x 有兼容问题）；JWT 让前端只需存一个字符串。
- 影响：多机部署必须显式设 `GWC_JWT_SECRET`，否则各机签发 token 互不认；上线前必须改掉默认管理员密码。

### ADR-013 依赖注入只传用户快照（AuthUser），不传 ORM 对象
- 日期：2026-10-20
- 状态：已生效
- 背景：M2 联调时 `PATCH /api/auth/me` 稳定 500。原因是身份依赖用 `get_db_or_none` 拿了一个 Session，
  接口参数 `db: DbSession` 又是另一个 Session，两个 Session 各自持有同一个 User 对象，
  提交时报 `Object is already attached to session`。
- 决定：`api/deps.py` 里解析出的用户统一转成不可变 `AuthUser`（uid / username / nickname / role），
  ORM 对象不跨依赖边界传递；需要完整用户信息（如 `create_time`）时，用接口自己的 Session 重新查一次。
- 理由：这类错误只在"两个 Session 并存"时出现，本地单库很容易蒙混过关，一旦并发或换库就会暴露。
  顺手也让"上报接口需要在数据库不可用时仍能识别游客"这件事变得自然。
- 影响：接口内不能再直接 `user.password_hash`，改密必须先 `repository.get_user(db, user.uid)`。

### ADR-014 识别图片只落盘不入库，静态目录单独挂载
- 日期：2026-10-20
- 状态：已生效
- 背景：M3 的图片识别要"结果可回看"（需求 5.3 的 `img_path`），但把图片二进制塞进 SQLite 会让库迅速膨胀，
  也不利于换库；同时前端需要一个能直接 `<img src>` 的地址。
- 决定：
  - `image_record.img_path` 只存**相对路径**（`2026-10/xxxx.jpg`），图片本体落在 `data/uploads/`；
  - 落盘前统一 EXIF 摆正、转 RGB、长边压到 1280（`config/app.yaml` 的 `upload` 节可调），手机原图 5MB 进来约 150KB；
  - 文件名用 uuid4，目录按月分片；不接受任何用户输入拼路径，`storage.resolve_rel_path()` 做越界校验；
  - 静态服务**只挂** `/media/uploads` 指向 `data/uploads`，不挂 `data/` 根目录——
    否则 `/media/app.db`、`/media/.jwt_secret` 会被顺带下载（已在 `scripts/test_api_m3.py` 加回归用例）；
  - 落盘失败或 `GWC_UPLOAD_ENABLED=0` 时，识别结果照常返回，只是 `img_url=null`、`img_path=""`。
- 理由：图片是"证据"，路径才是"数据"。库里存路径，换机器、换部署目录、换存储（本地→对象存储）都只改 `storage.py`。
- 影响：`.gitignore` 已忽略 `data/uploads/*`；新机器首次识别会自动建目录，不需要初始化脚本。

### ADR-015 截屏用 html2canvas，自检用 CDP 而不是 `--dump-dom`
- 日期：2026-10-20
- 状态：已生效
- 背景：🖐️ 截屏要"抓当前可视区"。`getDisplayMedia` 需要用户二次授权、还能截到桌面，超出"只操控当前标签页"的边界；
  html2canvas 纯前端、零授权，符合需求 3.6 的边界说明。
- 决定：
  - 用 html2canvas 1.4.1，**随 SDK 放在 `sdk/vendor/`**（195KB），默认从本地加载，离线可用；嵌入方可用 `scriptUrl` 指到自己的 CDN；
  - 截图参数：`x/y = 当前滚动位置`、`scrollX/scrollY = 0`（否则偏移两次）、`scale = min(2, devicePixelRatio)`；
  - 摄像头预览画布用 `data-gwc-ignore="true"` 标记后从截图中排除（写死 id 太脆，业务页换个 canvas 就失效）；
  - 产物只进内存（`ScreenshotStore`，默认留 5 张，objectURL 自动回收），🖐️ 不入库；🤟 才上传识别并写 `image_record`；
  - 自检用 `scripts/check_screenshot.mjs`：起无头 Chrome，**通过 CDP 主动轮询**页面状态，实测尺寸 / 颜色数 / 亮度 / 耗时。
- 理由：`chrome --dump-dom` 在页面 load 后立刻 dump，html2canvas 还没画完就拿到中间态（实测同一页面时好时坏）；
  CDP 轮询才能稳定复现。这条也是"无摄像头也要能验收"的一部分。
- 影响：`frontend/pages/selfcheck.html` 是常驻自检页；改动截屏相关代码后要跑
  `node scripts/check_screenshot.mjs`（5 个断言：尺寸、非空白、亮度、耗时、返回成功）。
